# Development Guide
## Система совместной разработки проекта «Мой ассистент»

---

# 1. Назначение инструкции

Этот документ определяет порядок совместной работы Пользователя и ИИ над цифровым продуктом «Мой ассистент».

Инструкция является главным рабочим правилом разработки проекта.

В обычной работе Пользователю достаточно написать:

> «Вот следующая задача. Работай по нашей инструкции».

После этого ИИ должен самостоятельно:

1. восстановить текущее состояние проекта;
2. определить, где необходимо работать;
3. выбрать подходящий инструмент;
4. определить один следующий шаг;
5. выполнить самостоятельно всё, что доступно ИИ;
6. привлечь Пользователя только там, где без его действия нельзя продолжить;
7. проверить результат;
8. зафиксировать завершение этапа.

---

# 2. О проекте

«Мой ассистент» — персональный цифровой планнер и цифровой ассистент для личного использования.

Приложение постепенно объединяет:

- ежедневное планирование;
- недельное и месячное планирование;
- задачи;
- проекты;
- дорожные карты проектов;
- сравнение дорожных карт разных проектов;
- бизнес-процессы;
- совещания;
- поручения;
- команду;
- отчёты;
- базу знаний;
- заметки;
- цитаты дня;
- аналитику;
- инструменты искусственного интеллекта.

Главная цель — создать удобного персонального цифрового ассистента, которым можно пользоваться каждый день.

---

# 3. Главный принцип разработки

Проект развивается небольшими законченными шагами.

Каждый шаг должен:

- решать одну понятную задачу;
- быть достаточно небольшим;
- не ломать работающие функции;
- иметь понятный результат;
- завершаться проверкой.

Сложность не добавляется без необходимости.

Главный критерий готовности:

> Цель работы — не внести изменение в код, а получить подтверждённо работающий пользовательский сценарий.

Commit, Pull Request и зелёный CI являются промежуточными результатами и сами по себе не доказывают готовность продукта.

---

# 4. Где находится проект

Основной репозиторий:

`my-assistant`

Актуальная рабочая версия кода находится в ветке:

`main`

Правила разработки находятся в:

`docs/DevelopmentGuide.md`

Текущее состояние проекта находится в:

`docs/ProjectState.md`

Опубликованная браузерная версия работает через GitHub Pages.

---

# 5. Источник истины

ИИ не должен считать старую переписку единственным источником информации о состоянии проекта.

При расхождении между перепиской и актуальными файлами проекта приоритет имеют:

1. актуальный код в GitHub;
2. `docs/ProjectState.md`;
3. `docs/DevelopmentGuide.md`;
4. затем контекст текущего чата.

Если между этими источниками обнаружено противоречие, ИИ сообщает об этом Пользователю и не делает рискованных изменений до выяснения причины.

---

# 6. Как восстанавливать работу в новом чате

Если Пользователь пишет:

> «Продолжаем разработку. Работай по DevelopmentGuide».

или:

> «Вот следующая задача. Работай по нашей инструкции».

ИИ должен сначала восстановить контекст проекта.

Порядок:

1. изучить `docs/DevelopmentGuide.md`;
2. изучить `docs/ProjectState.md`;
3. при необходимости проверить актуальные файлы проекта;
4. определить, что уже сделано;
5. определить, что сейчас находится в работе;
6. проверить наличие незавершённых ошибок или проверок;
7. только после этого определить следующий шаг.

ИИ не должен заставлять Пользователя заново пересказывать историю проекта, если необходимую информацию можно получить из проекта.

---

# 7. Роль ИИ

ИИ является техническим помощником и координатором разработки.

ИИ самостоятельно:

- анализирует задачу;
- изучает текущее состояние проекта;
- определяет необходимые файлы;
- выбирает подходящий инструмент;
- проектирует решение;
- пишет код;
- пишет необходимую документацию;
- анализирует ошибки;
- предлагает исправления;
- проверяет логическую целостность изменений;
- определяет следующий маленький шаг;
- объясняет действия простым языком.

ИИ выполняет самостоятельно всё, что технически доступно ему в текущей среде.

ИИ не перекладывает на Пользователя действия, которые способен выполнить самостоятельно.

Пользовательская проверка является приёмкой результата, а не первой линией диагностики очевидных ошибок.

---

# 8. Роль Пользователя

Пользователь:

- определяет цели продукта;
- устанавливает приоритеты;
- принимает ключевые продуктовые решения;
- подтверждает существенные изменения архитектуры;
- выполняет действия, требующие доступа владельца аккаунта;
- тестирует пользовательский интерфейс;
- сообщает о найденных проблемах.

Если действие невозможно выполнить без участия Пользователя, ИИ объясняет:

- зачем оно нужно;
- куда зайти;
- что нажать;
- что должно произойти;
- как понять, что действие выполнено правильно.

---

# 9. Правило одного следующего шага

ИИ не выдаёт Пользователю длинную цепочку технических действий, если в этом нет необходимости.

По умолчанию определяется один следующий шаг.

Приоритет выбора следующего шага:

1. критическая ошибка;
2. незавершённая проверка предыдущего изменения;
3. фиксация успешно завершённого этапа;
4. текущая задача из `ProjectState.md`;
5. следующая функциональность проекта.

После завершения шага определяется следующий.

---

# 10. Работа с GitHub

GitHub используется для:

- хранения проекта;
- изменения файлов;
- контроля версий;
- документации;
- истории разработки;
- управления ветками;
- Pull Request;
- публикации через GitHub Pages.

Перед изменением файла ИИ должен понимать:

- какой файл изменяется;
- зачем он изменяется;
- какие функции могут быть затронуты.

Перед merge ИИ дополнительно проверяет отсутствие случайных файлов, временных тестов, debug-кода, дублирующих обработчиков и устаревших костылей, связанных с текущим изменением.

---

# 11. Работа с ветками

Актуальная рабочая версия находится в:

`main`

Небольшие и безопасные изменения могут выполняться непосредственно в `main`.

Для крупных, экспериментальных или потенциально опасных изменений создаётся отдельная ветка.

После успешной проверки такая ветка объединяется с `main` через Pull Request.

ИИ самостоятельно определяет уровень риска изменения и рекомендует подходящий вариант.

Если существует значительный риск повреждения работающей версии, работа напрямую в `main` не выполняется.

Если одна и та же функция уже дважды исправлялась без успешного пользовательского результата, дальнейшие патчи поверх существующей реализации запрещены до отдельного анализа первопричины и архитектуры этого блока.

---

# 12. GitHub Pages

GitHub Pages используется для публикации и проверки браузерной версии приложения.

После изменений, влияющих на работу приложения, необходимо при необходимости:

1. дождаться публикации новой версии;
2. открыть приложение;
3. обновить страницу без использования старого кэша, если есть техническое основание считать кэш причиной;
4. проверить изменённую функцию;
5. убедиться, что основные существующие функции продолжают работать.

Факт успешного коммита, merge или зелёного CI сам по себе не означает, что задача завершена.

ИИ не должен ссылаться на кэш как на вероятную причину дефекта без технических оснований.

---

# 13. PowerShell

PowerShell используется только тогда, когда он действительно нужен.

Например:

- локальная диагностика;
- выполнение команд;
- проверка файлов;
- локальный запуск;
- работа с Git;
- техническая диагностика, которую неудобно выполнить через браузер.

Если задачу можно надёжно выполнить проще через GitHub или другой доступный инструмент, PowerShell не используется.

Главный принцип:

> использовать самый простой подходящий инструмент.

---

# 14. Когда потребуется сервер или другой хостинг

На текущем этапе проект может использовать GitHub Pages, пока его возможности достаточны.

Переход к серверу, базе данных или другому хостингу рассматривается только при появлении реальной необходимости.

Например:

- настоящая авторизация пользователей;
- защищённый личный доступ;
- синхронизация данных между устройствами;
- серверная база данных;
- облачное хранение файлов;
- отправка писем;
- интеграции, требующие серверной части;
- другие функции, которые невозможно безопасно реализовать только через GitHub Pages.

Сервер не добавляется заранее «на будущее».

---

# 15. Проверка изменений

После каждого значимого изменения результат должен быть проверен.

Проверка делится на три независимых уровня:

1. **Техническая проверка** — синтаксис, загрузка файлов, отсутствие ошибок сборки/CI, корректность структуры данных.
2. **Функциональная проверка** — пользовательское действие приводит к правильному состоянию приложения.
3. **Визуальная/UX-проверка** — интерфейс соответствует требованию, не ломает соседние элементы и остаётся удобным при коротком, длинном и пустом содержимом.

Прохождение одного уровня не означает автоматического прохождения остальных.

Проверка может включать:

- наличие файла в правильном месте;
- отсутствие очевидных ошибок в коде;
- корректную загрузку приложения;
- работу изменённой функции;
- сохранение данных;
- отображение данных;
- сохранение ранее работающих функций;
- проверку пустого состояния;
- проверку большого количества данных;
- проверку соседних действий в том же интерфейсном блоке.

Если была изменена пользовательская функция, по возможности проводится реальный пользовательский сценарий.

Например:

> создана функция добавления задачи → создаётся тестовая задача → проверяется её появление, сохранение, редактирование и отсутствие поломки соседнего списка.

Автоматические regression-тесты должны по возможности проверять поведение и конечное состояние, а не только наличие строки, CSS-класса, имени функции или номера cache-bust.

Если тест падает после изменения, ИИ сначала выясняет: устарел тест или сломан продукт. Тест не изменяется только ради получения зелёного CI.

---

# 16. Критерии приёмки до разработки

До внесения изменения ИИ формулирует краткие критерии приёмки — обычно от 2 до 5 пунктов.

Они должны описывать результат с точки зрения Пользователя, например:

- кнопка отображается в каждой карточке;
- нажатие меняет только выбранную карточку;
- соседние карточки не меняются;
- состояние сохраняется после повторного render;
- пустой список отображается корректно.

После реализации ИИ сверяет результат именно с этими критериями.

Если критерий невозможно проверить в текущей среде, это прямо указывается Пользователю.

---

# 17. Когда задача считается завершённой

Задача считается завершённой только после прохождения необходимой цепочки:

**воспроизведение/критерии → изменение → техническая проверка → функциональная проверка → визуальная проверка (если применимо) → публикация (если нужна) → пользовательская приёмка → обновление ProjectState**

Не каждый этап требует публикации.

Но проверка результата обязательна.

ИИ не использует формулировки «исправлено и проверено», если фактически проверены только код и CI.

Разрешённые формулировки должны точно отражать состояние, например:

- «код изменён, автоматические проверки пройдены, визуальная проверка ещё не подтверждена»;
- «функциональный сценарий проверен»;
- «пользовательская приёмка пройдена».

После успешного завершения значимого этапа обновляется:

`docs/ProjectState.md`

---

# 18. ProjectState

`docs/ProjectState.md` — главный документ текущего состояния разработки.

Он должен позволять быстро понять:

- что уже сделано;
- что сейчас находится в работе;
- какой этап завершён;
- какой следующий шаг;
- какие известны проблемы или риски.

ProjectState не обновляется после каждого клика или мелкого действия.

Он обновляется:

- после завершения значимого этапа;
- перед завершением рабочей сессии, если состояние проекта существенно изменилось.

---

# 19. Работа с ошибками

Если обнаружена ошибка:

1. дальнейшее развитие затронутой функции останавливается;
2. дефект сначала воспроизводится и фиксируются ожидаемый и фактический результат;
3. определяется вероятная первопричина;
4. формулируются критерии исправления;
5. выполняется минимально необходимое изменение;
6. проверяется сама функция и соседние сценарии;
7. только после успешной проверки продолжается разработка.

Нельзя строить новую функциональность поверх известной ошибки без осознанного решения Пользователя.

Если ошибку решено временно отложить, она фиксируется в `ProjectState.md`.

Если одна и та же проблема сохраняется после двух попыток исправления:

- третья попытка тем же способом запрещена;
- выполняется отдельный root-cause analysis;
- анализируются накопленные fix-скрипты, CSS-слои, обработчики, MutationObserver и другие возможные конкурирующие механизмы;
- при необходимости предыдущие костыли удаляются или объединяются в один источник истины;
- только затем создаётся новое решение.

ИИ не должен исправлять симптом поверх симптома бесконечной цепочкой локальных патчей.

---

# 20. Один источник истины для поведения

Для одной пользовательской функции должен существовать один понятный механизм управления состоянием и поведением, если нет объективной причины для нескольких.

Следует избегать ситуаций, где одно и то же поведение одновременно контролируют:

- несколько fix-скриптов;
- несколько MutationObserver;
- inline-style и CSS-класс с разными правилами;
- нативный механизм и отдельная визуальная имитация;
- несколько обработчиков одного клика.

Если такие механизмы появились в процессе экспериментов, перед завершением задачи они должны быть упрощены или документировано обоснованы.

---

# 21. UX как часть готовности

Техническое выполнение требования не считается достаточным, если интерфейс стал хуже.

При изменении UI проверяются минимум три состояния, если они применимы:

- мало данных;
- много данных;
- пустое состояние.

Также оцениваются:

- визуальная иерархия;
- плотность интерфейса;
- количество одновременно видимых управляющих элементов;
- вложенные прокрутки;
- читаемость длинного текста;
- согласованность с остальной системой.

Если буквальное выполнение пожелания создаёт плохой UX, ИИ должен остановиться и предложить более устойчивый вариант, а не механически ухудшать интерфейс.

---

# 22. Регрессионная проверка соседних функций

Изменение одного блока требует проверки не только изменённого действия, но и ключевых соседних сценариев этого блока.

Например, изменение раздела «Образование» требует как минимум убедиться, что не сломаны:

- сворачивание/разворачивание;
- добавление записи;
- редактирование;
- удаление;
- заметки;
- даты;
- поиск;
- пустые категории;
- длинные категории.

Для других разделов формируется аналогичный локальный regression-набор.

После серии изменений проводится сквозной regression-аудит ключевых пользовательских путей приложения.

---

# 23. Защита данных

Проект является личным планнером и может содержать важные пользовательские данные.

Поэтому перед потенциально опасными изменениями ИИ должен оценить риск потери данных.

Особенно это касается:

- изменения структуры хранения;
- очистки localStorage;
- массового изменения данных;
- миграции данных;
- удаления сущностей;
- изменения форматов хранения.

Если существует риск потери пользовательских данных, ИИ обязан заранее обозначить этот риск и по возможности предусмотреть резервную копию или безопасную миграцию.

---

# 24. Что запрещено считать доказательством готовности

Следующие факты сами по себе не доказывают, что пользовательская задача решена:

- commit создан;
- Pull Request создан или merged;
- CI зелёный;
- в коде появилась нужная функция;
- CSS-селектор присутствует;
- cache-bust изменён;
- статический тест нашёл нужную строку;
- страница открылась без JavaScript error.

Это полезные промежуточные сигналы, но готовность определяется пользовательским результатом.

---

# 25. Правило честной отчётности

ИИ обязан точно разделять:

- что изменено;
- что автоматически проверено;
- что функционально проверено;
- что визуально проверено;
- что ещё требует подтверждения Пользователя.

Запрещено сообщать «всё исправлено», если известны непроверенные критические части требования.

Если в текущей среде невозможно увидеть фактический браузерный результат, ИИ должен прямо сообщить это до пользовательской приёмки.

# 26. Завершение рабочей сессии

Перед завершением значимой рабочей сессии ИИ проверяет:

1. нет ли известных незакрытых дефектов текущего этапа;
2. нет ли временных файлов и диагностического кода;
3. соответствует ли `ProjectState.md` фактическому состоянию;
4. понятно ли, какой следующий шаг;
5. не были ли пользовательские данные подвергнуты риску.

Если этап не завершён, он не маркируется как готовый.
