# Data Store Design

## Проект единого слоя хранения и доступа к данным

Этот документ описывает следующий архитектурный слой проекта «Мой ассистент»: единый интерфейс между приложением и фактическим местом хранения данных.

Цель этапа — убрать прямую зависимость прикладной логики от `localStorage`, не меняя существующий формат данных и не затрагивая пользовательские данные.

---

## 1. Текущее состояние

Сейчас `app.js` напрямую работает с браузерным хранилищем.

Основной ключ данных:

`myAssistantProFinal.v1`

Текущая схема работы:

- при запуске приложение читает JSON из `localStorage`;
- прочитанные данные проходят существующую функцию `normalize(...)`;
- изменения состояния сохраняются через существующую функцию `persist(...)`;
- экспорт формирует JSON из текущего `state`;
- перед импортом создаётся резервная копия по ключу `myAssistantProFinal.v1.beforeImport`;
- после импорта данные снова проходят `normalize(...)` и сохраняются.

Эта схема работает и должна остаться совместимой.

---

## 2. Задача нового слоя

Новый слой должен стать единственным местом, которое знает, где и как физически сохраняются данные приложения.

Прикладная логика должна обращаться к нему, а не напрямую к `localStorage`.

На первом этапе слой продолжает использовать тот же `localStorage` и тот же ключ.

Новый слой не является новой базой данных и не должен менять пользовательские данные.

---

## 3. Предлагаемое расположение

Первый модуль:

`core/storage/data-store.js`

Он должен быть небольшим независимым модулем без логики интерфейса.

Модуль не должен знать о DOM, уведомлениях, тостах, экранах или маршрутах приложения.

---

## 4. Ответственность слоя

Слой отвечает только за операции физического хранения:

1. прочитать сохранённые данные;
2. сохранить переданные данные;
3. создать именованную резервную копию;
4. прочитать резервную копию;
5. сообщить об ошибке чтения или записи вызывающему коду.

Он не должен самостоятельно решать, как отображать ошибку пользователю.

---

## 5. Минимальный интерфейс v1

Предлагаемый публичный интерфейс модуля:

```js
MyAssistantDataStore.load()
MyAssistantDataStore.save(data)
MyAssistantDataStore.saveBackup(name, data)
MyAssistantDataStore.loadBackup(name)
```

Дополнительно модуль может публиковать неизменяемую конфигурацию текущего адаптера:

```js
MyAssistantDataStore.STORAGE_KEY
```

где значение остаётся:

`myAssistantProFinal.v1`

### `load()`

Читает основной ключ из `localStorage`.

Возвращает:

- сохранённый объект, если данные существуют и JSON корректен;
- `null`, если данных ещё нет.

При повреждённом JSON или недоступном хранилище должна возникать понятная ошибка, которую обрабатывает приложение.

### `save(data)`

Сериализует переданный объект в JSON и записывает его в существующий основной ключ.

Не изменяет переданный объект.

### `saveBackup(name, data)`

Сохраняет резервную копию в служебный ключ, образованный от основного ключа.

Для существующего импорта должно поддерживаться имя:

`beforeImport`

и фактический ключ:

`myAssistantProFinal.v1.beforeImport`

### `loadBackup(name)`

Читает и разбирает указанную резервную копию.

Если резервной копии нет, возвращает `null`.

---

## 6. Что остаётся вне слоя хранения

### Нормализация данных

Существующая функция `normalize(...)` пока остаётся частью текущей логики приложения.

Причина: нормализация определяет структуру и совместимость данных, а не механизм их физической записи.

На первом этапе нельзя одновременно переносить хранение и переписывать систему миграций.

### Начальные тестовые данные

`sample()` остаётся вне слоя хранения.

Решение использовать тестовые/начальные данные при отсутствии сохранённого состояния принимает приложение.

### UI сохранения

Текущие сообщения:

- «Сохранено локально»;
- «Ошибка сохранения»;
- пользовательские уведомления и `toast(...)`

остаются в прикладной части. Data Store только возвращает результат или ошибку.

### Экспорт и импорт файлов

Работа с `FileReader`, скачиванием JSON и интерфейсом импорта остаётся в приложении.

При этом импорт должен использовать Data Store для резервной копии и итоговой записи вместо прямого обращения к `localStorage`.

---

## 7. Совместимость

Первая реализация обязана соблюдать следующие ограничения:

- основной ключ остаётся `myAssistantProFinal.v1`;
- формат JSON не меняется;
- версия текущего состояния данных не меняется только из-за появления Data Store;
- существующие данные не очищаются;
- миграция не запускается только ради подключения нового слоя;
- резервная копия `beforeImport` остаётся совместимой с текущим поведением;
- стабильная модель задачи `core/models/task.js` не меняется;
- приложение после подключения слоя должно читать те же данные, что и до него.

---

## 8. Обработка ошибок

Data Store не должен скрывать ошибки хранения.

Ошибки чтения и записи должны быть доступны вызывающему коду, чтобы приложение могло:

- показать пользователю существующее понятное сообщение;
- не считать неудачную запись успешной;
- при неудачном импорте попытаться восстановить резервную копию.

На первом этапе не требуется сложная система классов ошибок. Достаточно предсказуемого поведения обычных JavaScript-ошибок.

---

## 9. Почему пока не нужен Repository для каждой сущности

На текущем этапе всё приложение хранит единый объект `state`.

Создание отдельных `TaskRepository`, `ProjectRepository`, `MeetingRepository` и других репозиториев сейчас добавило бы архитектурную сложность без практической пользы.

Поэтому сначала вводится один тонкий слой физического хранения всего состояния.

Отдельные репозитории или сервисы доступа к сущностям стоит вводить только тогда, когда конкретный раздел приложения будет переводиться на новый слой и появится реальная необходимость.

---

## 10. Путь внедрения

Внедрение должно происходить отдельным следующим этапом и минимальными изменениями:

1. создать `core/storage/data-store.js`;
2. подключить модуль до `app.js`;
3. заменить начальное прямое чтение `localStorage` на `DataStore.load()`;
4. заменить запись в `persist(...)` на `DataStore.save(state)`;
5. заменить прямые операции резервной копии импорта на методы Data Store;
6. не менять остальные части приложения;
7. проверить работу на существующих данных и на тестовом импорте/экспорте.

Эти действия не выполняются в рамках текущего документа.

---

## 11. Проверка будущей реализации

Перед объединением реализации с `main` необходимо проверить как минимум:

- приложение открывается с уже существующими данными;
- существующие задачи и проекты отображаются;
- новая задача создаётся и сохраняется после обновления страницы;
- завершение и повторное открытие задачи сохраняются;
- экспорт JSON работает;
- импорт корректного JSON работает;
- при импорте создаётся резервная копия;
- не появилось нового ключа для основных пользовательских данных;
- прежний ключ `myAssistantProFinal.v1` продолжает использоваться;
- пользовательские данные не очищаются.

---

## 12. Граница текущего этапа

Проектирование Data Store v1 считается завершённым, когда зафиксированы:

- назначение слоя;
- минимальный публичный интерфейс;
- граница ответственности;
- требования совместимости;
- обработка ошибок;
- безопасный порядок будущего внедрения;
- набор обязательных проверок.

Следующий отдельный шаг после принятия этого проекта — реализовать минимальный `core/storage/data-store.js` поверх существующего `localStorage` без изменения формата данных.
