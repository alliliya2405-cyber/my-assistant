# Data Model

## Модель данных проекта «Мой ассистент»

Этот документ описывает основные сущности данных приложения, их связи и правила дальнейшего развития модели.

Цель текущего этапа — сначала зафиксировать понятную модель данных и только после этого проектировать единое хранилище. Этот документ сам по себе не меняет способ хранения данных и не требует миграции существующего `localStorage`.

---

## 1. Общие правила

- каждая самостоятельная сущность имеет уникальный `id`;
- связи между самостоятельными сущностями хранятся через идентификаторы;
- задача может существовать без проекта;
- даты календарных событий хранятся отдельно от времени начала;
- продолжительность хранится в минутах;
- для изменяемых самостоятельных сущностей по возможности используются `createdAt` и `updatedAt`;
- существующие данные не переименовываются и не мигрируют только ради документации;
- модель расширяется постепенно, когда появляется реальная функция приложения.

---

## 2. Project — проект

Проект объединяет связанную работу и является верхним уровнем проектного планирования.

Текущие данные приложения уже используют для проекта следующие основные поля:

- `id` — уникальный идентификатор;
- `name` — название;
- `areas` — сферы, к которым относится проект;
- `goal` — цель;
- `meaning` — смысл проекта;
- `start` — дата начала;
- `end` — дата окончания;
- `roles` — роли пользователя в проекте;
- `status` — состояние проекта;
- `team` — участники проекта;
- `subprojects` — подпроекты;
- `sprints` — спринты проекта;
- `links` — связанные ссылки;
- `createdAt` — дата создания;
- `updatedAt` — дата последнего изменения.

Связи:

- один проект может содержать несколько подпроектов и спринтов;
- один проект может быть связан с несколькими задачами;
- один проект может быть связан с несколькими совещаниями.

На текущем этапе `team`, `subprojects`, `sprints` и `links` могут оставаться вложенными структурами существующего проекта. Выделять их в отдельное хранилище заранее не требуется.

---

## 3. Task — задача

Задача — основная единица ежедневного планирования.

Стабильная модель задачи уже реализована в `core/models/task.js`. Документ должен следовать этой модели, а не вводить параллельный формат.

Поля:

- `id` — уникальный идентификатор;
- `title` — название задачи;
- `description` — описание;
- `projectId` — связанный проект, может быть пустым;
- `subprojectId` — связанный подпроект, может быть пустым;
- `sprintId` — связанный спринт, может быть пустым;
- `meetingActionId` — связь с действием по итогам совещания, может быть пустой;
- `date` — дата выполнения;
- `start` — время начала;
- `duration` — продолжительность в минутах;
- `priority` — приоритет;
- `sphere` — сфера;
- `role` — роль пользователя;
- `method` — способ выполнения;
- `result` — ожидаемый или фиксируемый результат;
- `status` — статус задачи;
- `done` — совместимый признак завершения для существующей логики;
- `createdAt` — дата создания;
- `updatedAt` — дата последнего изменения.

Поддерживаемые сейчас статусы:

- `planned` — запланирована;
- `done` — выполнена.

Статусы `in_progress` и `cancelled` пока не вводятся: стабильная модель задачи их не поддерживает. Их можно добавить отдельным законченным изменением, если это потребуется продукту.

---

## 4. Meeting — совещание

Совещание хранит событие совместной работы и его результат.

Минимальная логическая структура:

- `id` — уникальный идентификатор;
- `title` — название;
- `date` — дата;
- `start` — время начала;
- `duration` — продолжительность в минутах;
- `projectId` — связанный проект, если есть;
- `participants` — участники;
- `result` — итог или протокол;
- `status` — состояние совещания;
- `createdAt` — дата создания, когда используется;
- `updatedAt` — дата изменения, когда используется.

Связи:

- совещание может быть связано с проектом;
- действие, возникшее по итогам совещания, может быть связано с задачей через `Task.meetingActionId`.

Точная нормализация совещаний должна выполняться только при отдельном этапе внедрения единого слоя данных. Текущую работающую структуру ради этого документа менять не нужно.

---

## 5. Habit — привычка

Привычка описывает регулярное действие пользователя, не обязательно связанное с проектом.

Минимальная логическая структура:

- `id` — уникальный идентификатор;
- `title` — название;
- `sphere` — сфера жизни;
- `schedule` — правило или расписание повторения;
- `duration` — обычная продолжительность в минутах;
- `status` — состояние привычки;
- `createdAt` — дата создания, когда используется;
- `updatedAt` — дата изменения, когда используется.

Привычка существует независимо от проекта. Детальная модель истории выполнения привычек не вводится до появления соответствующей функции.

---

## 6. Report / Plan — отчёт и план

В существующем приложении уже есть документы типа отчёта и плана. Они не должны теряться при будущем переходе к единому слою данных.

Основные поля существующей структуры:

- `id` — уникальный идентификатор;
- `type` — тип документа (`report` или `plan`);
- `title` — название;
- `department` — подразделение;
- `period` — период;
- `rows` — строки документа;
- `createdAt` — дата создания;
- `updatedAt` — дата изменения.

Строки `rows` пока остаются частью документа. Выделять их в самостоятельную сущность без практической необходимости не нужно.

---

## 7. Связи между основными сущностями

Основные связи:

`Project 1 → N Task`

`Project 1 → N Meeting`

`Project 1 → N Subproject`

`Project 1 → N Sprint`

Дополнительно:

- задача может существовать без проекта;
- задача может уточнять связь с подпроектом или спринтом;
- задача может быть создана из действия по итогам совещания;
- привычка существует независимо от проекта;
- отчёты и планы пока являются самостоятельными документами.

---

## 8. Текущее хранение данных

Сейчас данные приложения сохраняются локально в браузере через `localStorage`.

Это действующий и проверенный механизм, поэтому на этапе описания модели данных он не меняется.

Следующий архитектурный этап должен отдельно определить единый слой доступа к данным. Такой слой должен сначала работать поверх текущего локального хранения и сохранять совместимость с уже существующими пользовательскими данными. Переход к серверной базе данных не требуется до появления реальной необходимости.

---

## 9. Совместимость и миграции

Будущая реализация единого хранилища должна соблюдать следующие правила:

- не удалять существующие данные пользователя;
- не очищать `localStorage` как способ перехода на новую модель;
- распознавать существующий формат данных;
- при необходимости выполнять явную и проверяемую миграцию;
- сохранять обратную совместимость там, где она нужна для работающего интерфейса;
- сначала проверять миграцию на тестовых данных и только затем считать этап завершённым.

Особенно важно сохранить действующую модель задачи из `core/models/task.js` и её совместимость с полем `done`.

---

## 10. Граница текущего этапа

На этом этапе модель считается достаточно описанной для следующего архитектурного решения, если:

- основные существующие сущности перечислены;
- связи между ними понятны;
- модель задачи совпадает со стабильным кодом;
- существующее локальное хранение признано текущим источником данных;
- зафиксировано требование безопасной совместимости и миграции;
- не вводятся заранее сущности и статусы, для которых ещё нет необходимой функции.

Следующий отдельный шаг после принятия этой модели — спроектировать единый слой хранения и доступа к данным. Реализовывать его в рамках текущего документа не нужно.
