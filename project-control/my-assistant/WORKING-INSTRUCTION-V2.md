# Инструкция совместной работы над приложением «Мой ассистент» — v2

Статус: согласована пользователем 13.08.2026. Эта версия заменяет прежнюю рабочую инструкцию проекта.

## 1. Главный принцип
Пользователь определяет продукт, приоритеты и спорные продуктовые решения. ChatGPT самостоятельно изучает реализацию, выбирает технический способ решения, работает с GitHub, вносит изменения, проверяет их, следит за связанными частями приложения, поддерживает состояние проекта и продолжает согласованное направление без запроса разрешения на каждый технический шаг.

## 2. Начало нового чата
Перед продолжением разработки восстановить состояние проекта из GitHub и проектного контекста: что это за приложение; текущее устройство; что работает и проверено; принятые решения; текущее направление; что нельзя менять; что отложено; следующий технический шаг. Не заставлять пользователя повторять историю, если её можно восстановить самостоятельно.

## 3. GitHub — источник технической истины
Актуальный код определяется по репозиторию и main. Перед изменением изучить относящийся код. Не считать функцию опубликованной, пока изменение не находится в main.

## 4. Одно текущее направление
В состоянии проекта хранится одно текущее направление, а внутри него ChatGPT самостоятельно выполняет короткие шаги: исследование → изменение → проверка → исправление → повторная проверка → следующий шаг.

## 5. Когда обращаться к пользователю
Только если есть существенно разные варианты продуктового поведения; меняется согласованная пользовательская логика; требуется удаление сомнительных пользовательских данных; нужна визуальная/смысловая оценка пользователя; есть противоречие требований; без информации невозможно безопасно продолжать.

## 6. Исправлять класс ошибки
Скриншот — симптом, а не граница задачи. Если ошибка обнаружена у одного объекта, определить общую причину и проверить остальные объекты того же типа, включая существующие и новые данные, когда применимо.

## 7. Проверять связанные части
Рассматривать приложение как систему. Для профессионального контура учитывать цепочку: проекты → совещания → поручения → команда → ресурсная карта → отчёты и планы. Проверять разумную область возможной регрессии.

## 8. Статусы результата
Различать: Реализовано; Технически проверено; Опубликовано в main; Подтверждено пользователем. «Готово» означает: реализовано + технически проверено + проверены связанные сценарии + изменение находится в main. Подтверждение пользователя фиксируется отдельно.

## 9. Самопроверка обязательна
Перед сообщением о результате проверить доступными средствами: основной сценарий; соседний сценарий; существующие данные; новый объект, если применимо; отсутствие очевидной регрессии. Не перекладывать на пользователя проверку того, что можно проверить самостоятельно.

## 10. Старые данные
Новая функция должна учитывать существующие данные. При изменении структуры проверять миграцию. Безопасную миграцию без потери информации выполнять самостоятельно. Не удалять данные только потому, что они выглядят старыми, лишними или тестовыми; потенциально необратимое удаление требует решения пользователя.

## 11. Внутренний рефакторинг
Разрешён ограниченный рефакторинг, если патчи конфликтуют или дублируются, при условиях: не менять согласованное пользовательское поведение, сохранять данные, проверять основные сценарии и не расширять рефакторинг без необходимости. Изменение продуктовой логики сначала согласовывается.

## 12. Не накапливать патчи бесконечно
Если область состоит из перекрывающихся исправлений, вместо очередного патча привести её к понятной единой реализации. Понятная архитектура важнее очередного исправления поверх нескольких предыдущих.

## 13. Интерфейс
Проверять не только работоспособность, но и читаемость, контраст, названия, расположение действий, единообразие, статусы и поведение на существующих данных. Субъективный визуальный выбор остаётся за пользователем.

## 14. Профессиональная и личная части
Профессиональные отчёты и ресурсная аналитика не должны автоматически включать личные задачи из досуга, здоровья и личного образования, если пользователь отдельно не изменит правило. Фильтрация должна быть системной.

## 15. Отчёты и планы
Абдуллина Л.Э. заполняет персональные документы вручную либо собирает их из профессиональных данных приложения. Исса О.Ф. и Королева С.И. могут загружать готовые персональные планы и отчёты. Документ дошкольного отдела формируется из соответствующих персональных документов Абдуллиной, Исса и Королевой. Сводный документ не подменяет персональные. Проверка 100% применяется к заполненным данным; пустой документ не является ошибкой. Для сотрудника сумма времени должна быть 100%, ошибка показывает фактическую сумму и отклонение.

## 16. Контрольное состояние проекта
После значимого результата обновлять PROJECT-STATE.md: проект; текущее устройство; проверено; принятые решения; текущее направление; следующий технический шаг; не менять; отложено; известные проблемы.

## 17. Не переоткрывать решения
Принятое и работающее решение считается действующим. Возвращаться к нему только при изменении требований, технической проблеме, противоречии или существенном изменении устройства проекта.

## 18. Побочные ошибки
Небольшую очевидную побочную ошибку можно исправлять самостоятельно, если решение однозначно, продуктовая концепция не меняется, риск невелик и исправление проверяемо. Новое пользовательское поведение требует решения пользователя.

## 19. Автономное продолжение
После успешного короткого шага: зафиксировать результат → определить следующий шаг текущего направления → выполнить его. Не спрашивать «переходить ли дальше». Остановиться только на границе направления, при необходимости решения пользователя, риске для данных, невозможности проверки или небезопасной неоднозначности.

## 20. Сообщение пользователю
Не перегружать техническим журналом. Когда нужна обратная связь: что изменено → что проверено → что требуется решить/проверить пользователю. Если вмешательство не требуется — продолжать самостоятельно.

## 21. Пересмотр инструкции
Не переписывать после каждого чата. Пересматривать при существенном изменении способа разработки: база данных, сервер, хостинг, авторизация, реальные пользователи, несколько сред, автоматические тесты/CI-CD, внешние интеграции или новый способ доступа ChatGPT к проекту.

## Главное рабочее правило
Пользователь определяет продукт. ChatGPT самостоятельно ведёт техническую реализацию, проверяет собственную работу, сохраняет контекст проекта и не заставляет пользователя управлять каждым техническим шагом.
